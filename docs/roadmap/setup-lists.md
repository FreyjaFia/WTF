## Setup lists (units, categories and similar) [Planned, added 1 Nov 2026]

**Built (7 Nov 2026): the Setup page.** `/management/setup` is a card hub, one card per list with a title, a short line and an "N active" count, grouped under Menu and Inventory headings that each have a one-line subtitle (like the Reports catalog). A card opens `/management/setup/:kind`; the page title there has the standard ghost back button to the hub. A small registry (`features/management/setup/setup-kinds.ts`: id, label, group, description, who can open it) drives it; the first four kinds are Categories, Sub-categories, Add-on Types (read by `ProductsRead`, written by `ProductsWrite`) and Waste Reasons (Admin and Super Admin). Roles only see the cards they can open, and a kind they cannot open lands on the hub. `/management/catalog` and `/management/waste-reasons` redirect here; one sidebar link (gear icon) and one Management tab (Setup). Setup stays a child of Management on purpose (a new top-level item would crowd the phone dock); revisit when it holds real settings such as branding, printers or branches. The Management group now uses a briefcase icon. The Catalog, Waste Reasons and Expenses lists have sortable headers like Users and Products; Expenses keeps its own page with a filter drawer. **Error and empty states** follow the Users page everywhere in Setup, Expenses and the hub: a failed connection (status 0, mapped in `CatalogSetupService`) shows the shared "Unable to connect" panel inside pull to refresh, and an empty list shows the empty-state card. **Not yet generic:** each kind still has its own list component and dialog; a shared list component driven by field config is the next step when a fifth kind (units) is added.

Several lists the app depends on are fixed in code, so changing them needs a release. Move each into its own table with a management page (Management > Setup), in the style of the Dynamic Catalog Management section below, so the owner can add and rename entries without a developer.

- **Inventory units first.** Today the allowed units (piece, box, pack, case, bottle, carton, cup, lid, sleeve, liter, milliliter, kilogram, gram) are a list in `ItemValidation.Units` (API) and `INVENTORY_UNIT_OPTIONS` (POS), kept equal by hand. The API now refuses any unit outside the list (1 Nov 2026), because items created with "ml" or "pc" showed an empty, required Base unit in the editor. Plan: a `Units` table (value, label, abbreviation, sort order, active; soft delete like the other management records), a `/api/units` list the POS and API both read, a management page to add and rename units, and the validators and `InventoryUnitLabels.Abbreviate` reading the table instead of a list. Existing items keep their unit text; the migration seeds the thirteen current units and maps old abbreviations ("pc", "ml", "g", "kg", "L") to them.
- **Same pattern for the other fixed lists:** categories and sub-categories, add-on types (with their rules), waste reasons (already a table with a page), stock adjustment reasons, payment methods and order sources. Review each for "needs a release to change" and move it when it bites.
- **Open questions:** may a shop add its own unit conversions (a carton is 24 bottles) here, or does that stay with the item (`StockUnitName`, `UnitsPerStockUnit`)? Who may edit the lists (Admin and Super Admin, assumed)?
